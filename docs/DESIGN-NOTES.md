# Design notes

为什么是读屏，而不是接管浏览器；以及那些踩过的坑。

## 1. 三条浏览器接管路线，逐一失败

在做出这个方案之前，先花了一整晚确认"常规路线真的走不通"。

| 路线 | 做法 | 结果 |
|:---|:---|:---|
| 自动化工具自带 Chromium | 直接启动 | 启动即崩，不写 `DevToolsActivePort` |
| 指定系统浏览器（Edge） | `--executable-path` | 进程起得来，CDP 握手全部静默挂死 |
| 克隆用户配置 + 调试端口 | 复制 `User Data` 到独立目录后启动 | 端口一度打开，随后进程在数分钟内被安全软件终结 |

补充一个容易被忽略的事实：**Chrome / Edge 111+ 在默认配置目录下会主动忽略 `--remote-debugging-port`**，这是防恶意软件窃取登录态的设计，不是配置错误。所以"端口不开"不等于命令写错了。

三次不同方式全部失败 → 判定为环境层面的主动防御，停止尝试。出于刷几个页面去关闭安全软件或加白名单，成本收益完全不成立。

## 2. 换到读屏之后的真实成本

读屏不是免费的：

- 每一步要一次截图 + 一次视觉推理，端到端比协议级自动化慢一个量级
- 坐标依赖视觉模型的位置判断，模型报错位置就会点偏
- 页面改版后旧坐标作废

它的价值不在快，在**几乎无差别兼容**：只要人眼看得到、鼠标点得着，就能操作。对于"只此一次、几十步"的任务，这个交换是划算的。

## 3. 那个吃掉了一小时的 bug

症状：点击后页面毫无变化。第一反应是"页面有透明遮罩拦截点击"，于是去找遮罩、去关侧栏、去试 UIA 元素树——全部无效。

真因：**DPI 缩放**。

| 项 | 值 |
|:---|:---|
| 系统缩放 | 150% |
| 截图实际像素 | 1920 × 1200 |
| pyautogui 默认视角 | 1280 × 800 |
| 后果 | 所有点击偏移 1.5 倍 |

更麻烦的是，那一晚**有一条消息曾经"发送成功"过**——纯属坐标恰好擦边。这个偶然的成功把排查方向带偏了很久。

教训写进 skill 里了：**判断自动化是否可靠，要看"换个位置还成不成"，不能看"这次成了"。**

## 4. 为什么坚持"一次只做一个动作"

连续盲发多个动作看起来高效，实际是失控的根源：

- 中间任何一步错位，后续动作全部打在错误的位置上
- 出错后无法判断是哪一步开始偏的，只能从头再来
- 而截图验收的成本很低（一次 grab + 一次读图）

所以整个流程被强制拆成：**做一个动作 → 截一次图 → 确认变化 → 下一个**。

## 5. 为什么人类必须在环

对外动作（发消息、提交表单、发布内容）代表的是**用户本人的身份**，不是工具的身份。所以：

- 最终内容必须给用户过目
- 用户点头之后才执行
- 执行完把实际发送的内容原样复述，而不是只说"已发送"

这条不只是合规考虑。它让用户对"以自己名义说出去的话"保有最终判断权——这在一份工具里是必须保留的。

## 6. 关于失败两次就换路

硬磕是这类自动化最贵的错误。坐标点不进去的时候，让用户手动点一下输入框，然后只做键盘动作（粘贴 + 回车），往往三秒解决，比再试五个坐标快得多。

所以 `SKILL.md` 里写了一条：**同一动作失败 2 次即停止**，换方案。用户说"算了"的时候，立刻停手、清理临时文件、给纯手动的最短路径。
